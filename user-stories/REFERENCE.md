# Reference

## Actors and boundaries

- **Account holder**: a person registering, authenticating, recovering credentials, changing settings, using invitations, or requesting account data actions. Account Kit does not supply a frontend.
- **Application**: owns user model, route mounting or controllers, validation and response design, signup eligibility, invitation authorization, profile fields, notification delivery, translation policy, account-domain data and authorization callbacks. There is no universal application role built into Account Kit.
- **Application operator**: installs/configures providers, migrations, session/auth/limiter/mail integration, enables optional capabilities, schedules pruning and uses Ace commands. Shell-only operator services are not an HTTP authorization boundary.
- **Social provider**: configured Ally integration (currently Google/GitHub recipes) that returns provider identity to the application flow.

## Public package surface reviewed

The root export map is [`index.ts`](../index.ts). It exposes `AccountKit` and `defineConfig`; configuration/stub setup; public account types and errors; Lucid adapter types and factory; `createAllySocialProvider`; `accountErrorResponse`; `passwordChangeRevision`; translator, prune and maintenance types; mail provision classes and URL/render/readiness helpers; and log/mail notification helpers and types. Separate public adapter factories are exported from [`adapters/lucid.ts`](../adapters/lucid.ts), [`adapters/sql.ts`](../adapters/sql.ts), [`adapters/drizzle.ts`](../adapters/drizzle.ts) and [`adapters/prisma.ts`](../adapters/prisma.ts). The testing subpaths in [`package.json`](../package.json) expose [`assertUsersAdapterContract`](../testing/adapter_contract.ts) for custom adapter conformance fixtures and [`captureNotifications`](../testing/notifications.ts) for in-memory application-test callbacks; see US-ACCOUNT-54 and US-ACCOUNT-55 for their effects and limits. The optional admission entry point [`src/admission/main.ts`](../src/admission/main.ts) exposes `defineAdmission`, `AccountAdmission`, admission middleware, invitation evidence/deletion cleanup hooks, admission errors, and admission config/decision/record types. Stories US-ACCOUNT-56 through US-ACCOUNT-58 cover current status, transaction-aware record checks, and domain preflight respectively. The HTTP entry point is documented in [managed HTTP](../docs/guide/managed-http.md); its route registration is opt-in.

## Managed password fields

The default managed JSON validators require confirmation fields alongside the service inputs: password change uses `newPasswordConfirmation` equal to `newPassword`; reset, activation and invitation acceptance use `passwordConfirmation` equal to `password`. These fields belong to the HTTP schemas, not the corresponding service method signatures. Managed signup (US-ACCOUNT-02) uses `passwordConfirmation` equal to `password` in its default validator. Invitation acceptance and signup may replace their validators through managed extensions. The `registration.register` service does not take a confirmation argument.

`Current` means source exposes a journey when enabled/configured; it is not a runtime test result.
