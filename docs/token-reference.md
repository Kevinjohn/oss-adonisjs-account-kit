# Access-token API reference

How the [API example](../examples/api/README.md) wires opaque access tokens through its own controllers. File paths are relative to
`examples/api/`.

## Configuration

Set `ACCOUNT_KIT_AUTH_STRATEGY=access_tokens` and use the existing `api` AdonisJS guard with its opaque access-token provider. The example config sets `tokenExpiresIn: '1d'` and `tokenAbilities: ['*']`; choose a shorter lifetime and narrower abilities for your application. `auth_access_tokens` must exist before token login. The example checks `invitations:create` before its invitation-send action. Other application routes must check their own required abilities.

Invitation list, resend, and revoke use the configured invitation authorization callbacks; this reference does not impose token-ability names on those operations. Add explicit ability checks if your application's token policy requires them.

Use HTTPS, a fixed public `APP_URL`, and trusted proxy configuration before using `request.ip()` for login limits. The configured registration-field policy and invitation authorization callback remain application decisions.

The shipped example config and Vine request validators share the 8–256 character policy for newly established passwords. If you change `passwordPolicy`, update the application's Vine rules to match; package service checks remain authoritative for registration, activation, invitation acceptance, password reset, and password change. Login accepts existing credentials separately and does not apply new-password rules.

## How it works

POST `/api/v1/auth/login` accepts `email` and `password`. A successful login issues an opaque token with the configured lifetime and abilities and returns it once in the JSON response. Send that value in `Authorization: Bearer <token>` to GET `/api/v1/account/profile` or other protected routes. The current-account response is allowlisted: it does not contain a password hash, proof, provider secret, raw provider response, or adapter internals. A limited inactive credential may reach account activation and email correction routes, while verified routes return 403 `E_ACCOUNT_KIT_UNVERIFIED_EMAIL`.

POST `/api/v1/account/logout` deletes only the current token. The second request with that token is unauthenticated (401). It does not revoke other tokens. Password reset, confirmed-email change, activation claim, and restriction changes revoke every current token. The self-service password-change endpoint passes the current token ID as `keepCurrent`: that token remains usable and every other token ends. If the current ID cannot be matched, every token ends; a service call that omits `keepCurrent` ends all tokens. These changes also advance the credential revision. Application-owned protected routes must apply the same authentication and account-access middleware to reject a token invalidated between guard authentication and route execution. Direct writes to account security columns are outside that guarantee; use the public account operations.

PATCH `/api/v1/account/profile` requires `currentPassword` and accepts `email` and the example's configured `fullName` field. It uses the public profile operation: an active account keeps its current email until the proposed address is confirmed; submitting the confirmed address cancels a pending change. Correcting an inactive account's address updates both address columns and revokes its existing tokens. The application field policy maps `fullName` before the adapter writes it. Other request fields are not writable through this route.

Password reset, activation, invitation, and email-change links use `/:token` path segments. GET inspects a proof without changing account state; POST on the same path completes it. Every proof response has `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. Redact these route paths and their token segments from access, proxy, tracing, and error logs: `/api/v1/auth/password-reset/:token`, `/api/v1/auth/email-verification/:token`, `/api/v1/auth/invitations/:token`, and `/api/v1/auth/email-change/:token`. Never put bearer credentials in URLs or logs. Client storage is an application threat-model decision; this example does not provide a browser token-storage SDK.

Activation completion at POST `/api/v1/auth/email-verification/:token` requires a fresh `password` and matching `passwordConfirmation`. This proves ownership of the address while replacing the password chosen before verification; all existing account tokens are revoked. The user must log in with the new password afterward.

Package-defined account errors use `{ "errors": [{ "code": "...", "message": "..." }] }`. With `Accept: application/vnd.api+json`, the entry uses `title` in place of `message`. Authentication failures are 401, forbidden or unverified access 403, invalid proofs 400, conflicts 409, and rate limits 429. Request-schema failures retain AdonisJS Vine's 422 response. Duplicate signup is an intentional Vine exception: it returns 422 with `field: "email"` and `rule: "unique"`, without distinguishing the existing account's state. Proof failures share a generic message, including missing, expired, replayed, or mismatched proofs. Package-defined errors extend `AccountKitError`; raw database and application callback errors may continue through normal application reporting. Committed delivery-path failures use `DeliveryError`; failed post-commit observers or follow-ups use `PostCommitError`, which can also wrap notification callbacks on observer paths. Both mean the operation committed, but only `PostCommitError` maps with `committed: true`. Handle them at the operation boundary, preserve the flow's normal success acknowledgement, and report the failure privately. The example outbox persists password-reset-completion and password-change notices only; it does not persist password-reset link delivery, signup activation, invitations, email-change, or other notices. A failed reset-link delivery receives the generic reset acknowledgement; the person can submit another generic password-reset request. For a committed signup failure, check whether the account exists and direct the person to request a new verification link. For a committed invitation failure, check whether the invitation is still pending: resend a pending invitation, or direct an already-accepted user to sign in or reset their password. Do not repeat signup or invitation acceptance, which can create a duplicate-account error or consume a different invitation.

## Files

`app/controllers/access_tokens_controller.ts` adapts package login and logout to the existing guard. The password-resets, email-verifications, invitations, account-password, and profile controllers adapt the account flows. `app/services/http_responses.ts` shapes HTTP errors and proof headers, and `app/exceptions/handler.ts` maps known package errors while allowing unknown errors through normal application reporting. `app/middleware/account_access_middleware.ts` and `app/middleware/verified_account_middleware.ts` gate application-owned routes. `start/routes.ts` selects the guard and exposes the reference endpoints. Functional tests exercise the installed archive on SQLite and PostgreSQL.

## Before deployment

Provision the token table and migrations, configure real notification delivery and URL destinations, select a suitable token lifetime and abilities, and protect every application-owned route that relies on revocation or active-account state. Redact proof paths and the Authorization header in all infrastructure logs. Operate the notification worker for password-reset-completion and password-change outbox rows. A password-reset link-provision failure is not persisted there; accept another generic reset request to issue a replacement link. Build durable delivery for other notices in application-owned storage if needed. Run the packed consumer checks on both supported databases after changing guard or account configuration.
