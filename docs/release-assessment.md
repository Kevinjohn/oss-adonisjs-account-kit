## Phase 1 scenario traceability

These are scenario-to-test mappings, not pass claims. Candidate-specific outcomes belong in the final pull request check record. The installed-consumer command must use the same immutable archive for every database, guard, and supported schema variant in the declared matrix.

### Packed managed-setup procedure

The packed consumer harness is a reference integration, not managed onboarding: `runFresh` copies `examples/api`, runs the basic `ace configure`, and retains that app's controllers and routes. For actual managed setup, install the exact candidate archive into a clean minimal Adonis application and follow [the published setup procedure](setup.md#prove-revocation-before-route-activation), including its inert-bootstrap steps. Keep `authentication.applicationRouteRevocation` false for the first `account-kit:setup --apply`; that writes the generated account guard and access middleware plus an inert owned route mount, so it does not mount managed endpoints. Review and explicitly run migrations, attach the generated middleware to an application-owned protected route, and establish a credential through the generated guard adapter. Prove that this credential is initially allowed, then use the public revocation operation selected by the setup choices: change its password when `emailPasswordManagement` is enabled; request and complete a reset when only `passwordReset` is enabled; or restrict and restore the account through `authentication.changeRestriction` when authentication alone is enabled. The same original credential must be denied after the selected operation; for restriction changes, also prove a fresh credential succeeds after restoration. A denial without the preceding successful request does not prove revocation. For session guard setup while the mount is inert, provide an application-owned CSRF bootstrap using the maintained session controller and route registration; setup reports a managed CSRF endpoint only if that endpoint is enabled by the selected capabilities and active mount. Only after the required revocation check passes, set `applicationRouteRevocation` true and reapply to activate the generated mount. Then run `account-kit:setup --check --production`, boot the app, and exercise the generated routes over HTTP without reference flow controllers. `workflowVerified` remains false until those runtime workflows are checked. Retain the selected choices, both generated-file diffs, setup reports, migration output, both protected-route responses, bootstrap result where applicable, boot/route-graph result, and positive and negative managed HTTP responses with the archive identity in the final PR check record. Run this for the required database and guard combinations. `tests/setup.spec.ts` and `tests/managed_http.spec.ts` provide source-level coverage; neither replaces this packed installed procedure.

## Schema and migration traceability

`configure.ts` exports nine package migration names: `create_password_reset_tokens`, `create_account_invitations`, `create_account_email_changes`, `add_email_verified_at_to_users`, `create_account_transaction_lock`, `evolve_identity_contract`, `create_social_identities`, `retire_account_email_changes`, and `add_credentials_changed_at_to_users`. `src/setup/plan.ts` derives applicable migration files from that list and omits `create_social_identities` when social is not selected. ## Supported boundaries and release limitations

- D10: notification work occurs after commit through `sendLater`; default delivery is best effort. The package ships no queue or outbox. Durable delivery is application-owned, recommended rather than required, and only supported as a readiness claim after the worker, retry, and outbox path is verified.
- D17: distribution is planned for `adonisjs-account-kit`, MIT, AdonisJS 7 and Node 24 or later, with first publication planned for `0.1.0`. This assessment is not publication approval.
- D22: deploy in a maintenance window: stop old instances, run migrations, then start new instances. Mixed-version overlap is unsupported. Migration rollback is supported only before the new version writes data; outstanding supported proofs survive upgrade.
- Setup requires an explicitly installed TypeScript parser supported by the package (`5.9.3+` within major 5 or `6.0.3+` within major 6). The parser is loaded for setup only. Setup inspects syntax and the selected environment values without executing application code. Unsupported dynamic expressions or indirect factories require manual reconciliation and runtime verification.
- Automatic Lucid model inspection is limited to a contained `#models/user` mapping to a direct native `BaseModel` class or the stock `UserSchema`/`withAuthFinder` composition. The effective class must expose exactly one physical `id` primary column with the chosen TypeScript identifier type; supported package aliases must resolve to the inspected files. `tests/setup.spec.ts` — `every supported User inheritance form checks its final default table` proves that the supported inheritance paths use the final class's default table and accept a custom selected table when it is explicitly declared; a renamed model must declare the matching table. The stock composition path follows imported base/schema and kernel/router service provenance only where the setup inspector can prove those bindings; arbitrary mixins, constructors, custom class decorators, decorated accessors, runtime metadata hooks, linked schema leaves, and other dynamic class initialization require manual reconciliation before migrations can be generated. Static inspection does not prove the final model behavior at boot.
- Setup resolves the selected `DB_CONNECTION` and session selector using process environment and Adonis environment-file precedence. It reads only the named values and blocks apply when the selected database or session store is ambiguous, unresolved, linked, or unsupported; an unknown database is an error, not a request for post-apply verification. It does not run migrations or establish that a live external database or deployment environment is available.
- Managed sessions are automatically wrapped only when setup can prove the actual imported native factory behind the selected session entry; it follows that factory rather than trusting the store alias string by itself. The source test demonstrates this boundary: an alias named `cookie` backed by the database factory is accepted, while an alias named `database` backed by the cookie factory is rejected. Cookie-backed sessions cannot provide server-side revocation; production memory storage cannot satisfy persistent-session claims. Custom or dynamic session configuration requires an application-owned wrapper and a truthful verifier for the selected server-side store and central destroy/revocation behavior. Verify middleware order and logout replay after application boot.
- `FRONTEND_URL` is the conventional trusted frontend-origin variable; setup may be given another selected variable name. Production backend and frontend origins require trusted HTTPS. Static checks cannot establish proxy behavior or arbitrary runtime configuration.
- Presence of callback files does not prove callback contracts or delivery. `policy.callbacks`, `mail.callbacks`, `externalConfigured`, `workflowVerified`, `migrationsApplied`, and `productionReady` are distinct evidence states. Do not turn unknown into pass: static `configurationValid` does not prove the registered route graph, callback behavior, real mail transport, applied migrations, or production readiness.
- Maintained Mail inspection blocks unsupported outer configuration and selectors, detected mutation of inspected Mail or environment bindings, missing selected mailers, and plainly non-callable providers before apply writes files. An opaque custom factory requires manual verification, and even a recognized native transport remains unverified until its selected configuration and delivery are checked. Static Mail inspection never establishes recipient delivery.
- Setup's lock coordinates setup runs in one workspace, not arbitrary editors or processes. Password-retirement inventory is point-in-time, reads password state through the configured adapter, does not inspect provider identities, and requires the declared maintenance window even when impact is zero.
- Application-owned routes must use the selected account-access middleware when they need account-revision or restriction checks. Excluded or replaced routes remain responsible for input validation, response mapping, authentication, CSRF, and access policy. Direct account writes can bypass package revocation hooks.
- Social identity is Phase 2 and excluded from these Phase 1 gates. `approved-pending` is not an implemented or verified provider flow.
- The [#49 technical evaluation](developer-evaluation.md) is this run's D23 fallback evidence. It records four documentation-guided task passes and the setup-origin and static migration-status observations. Local callback capture is not recipient delivery. Human participation, novice usability, participant success measures, elapsed-time results, PostgreSQL evaluation, and recipient delivery remain unverified.

The final PR must attach exact-source and exact-archive check results after source review and the required database/guard matrix complete. Until then, this document defines coverage and limits only; it makes no release-readiness claim.
