# Account Kit setup

## Configuration

After installing the package, add `() => import('adonisjs-account-kit/commands')` to the application's `adonisrc.ts` `commands` array. Do this before running setup; the basic `configure` command creates its own starter config and is a separate path. Setup requires a separately installed TypeScript 5.9.3 or newer 5.x, or 6.0.3 or newer 6.x, to inspect executable application configuration without running it; install the supported version explicitly with `pnpm add -D typescript@^5.9.3` if missing. Other Account Kit entry points do not load TypeScript. Run `node ace account-kit:setup` for the interactive choices, or copy the [session example choices](setup_choices.example.json) or [API starter token choices](setup_choices.api.example.json) into the application and pass `--input=path/to/choices.json`. The session example expects an existing `web` session guard; the API example expects an existing `api` access-tokens guard. Both examples select authentication, so they require an application-owned `accountKitPolicy.canAccess` callback before preview or apply. Inspect your application's `config/auth.ts` and choose its actual guard. Both paths produce the same typed setup choices. `--apply` writes the proposal; without it the command previews. `--check` reads the persisted choices and diagnoses the current application without writing. Add `--production` to check public origin and session security requirements for deployment.

The file `config/account_kit_setup.json` records the six pillars. `features` selects underlying account services; `managed` selects maintained endpoint groups and must be a subset of `features`. This allows an application-owned login alongside managed password reset. `managedExcept` optionally names specific managed endpoints to leave to an application-owned route on the same method and path; it defaults to `[]`. Choose the exclusions in the setup input, then add the replacement application route. The replacement must provide its own proof-response protection, including early headers for parser and CSRF failures; see [manual verification steps](#manual-steps). Do not hand-edit the generated route mount. If a prior manual edit already exists, reconcile it with a clean generated mount before applying the updated choices; setup preserves that owner edit as a conflict until you do. A single managed group uses one existing named `session` or `access_tokens` guard. Setup never creates a guard or changes the application's default guard. `routePrefix` identifies the managed route prefix. The supported identity mapping uses the default Lucid connection, an `id` primary key of integer, string, or UUID type, and the conventional `email`, `password`, and `email_verified_at` columns. Custom adapters require a separate contract review.

For `access_tokens`, set `authentication.token` to `{ "revocation": true, "lifetime": "1d", "abilities": ["*"] }` or narrower abilities appropriate for your application. `revocation` must be true, `lifetime` must be a supported positive duration, and `abilities` must be nonempty. Set `authentication.applicationRouteRevocation` true after attaching and verifying the generated account-access middleware on application-owned protected routes. A session selection uses `authentication.session` instead; its four booleans record checks that must be performed, rather than configuring the session backend themselves.

The `mail` pillar stores environment variable **names** for the sender, transport, trusted backend origin, and trusted frontend origin. The conventional frontend reference is `FRONTEND_URL`; an explicitly selected custom name is also supported. When only authentication is selected as a service and no email capability is enabled, the report marks mail and delivery not applicable and generates empty URL and notification callbacks; Mail installation, action destinations, and origin references are not prerequisites for that selection. The examples select maintained AdonisJS Mail: install `@adonisjs/mail` 10 with `pnpm add @adonisjs/mail@^10`, run `pnpm exec node ace configure @adonisjs/mail` to create `config/mail.ts` and register its provider, then configure a real transport and the required environment values. Setup blocks selected Mail entries that are plainly not callable, unsupported outer configuration or selectors, and detected changes to inspected Mail or environment bindings. An opaque custom selected factory requires manual verification; even a recognized transport still needs a delivery check. Check the resulting provider and config before applying setup. The pillar stores safe relative paths for the relevant action destinations; it does not store origin or secret values. In production, public backend and frontend origins must use HTTPS. Development HTTP is limited to loopback origins. Origin base paths are retained. Mail delivery is either `best-effort` or application-owned `durable`; durable classification requires custom notification callbacks and an independently verified worker and retry path. A database commit and message delivery are separate outcomes.

To use your own notification transport, set `mail.integration` to `custom`, `mail.senderEnv` and `mail.transportEnv` to `null`, and provide `app/services/account_kit_notifications.ts` exporting `accountKitNotifications: Partial<NotificationCallbacks>` from the package root. Implement `passwordResetProvision`, `accountActivationProvision`, `emailChangeProvision`, `emailChanged`, `passwordResetCompleted`, and `passwordChanged` for the five-service examples; invitations also require `invitationProvision`. Provision callbacks receive an action URL and must hand it to a real delivery transport. A local file capture can help inspect links in development, but it is not message delivery or a production-ready transport. `delivery: durable` additionally requires an application-owned queue or outbox with a verified worker, retries, and terminal-failure handling.

The following complete callback shape writes a **development-only** private capture file. Use it to inspect links locally, then replace `capture` with your configured delivery operation before deployment. Do not commit the capture file or treat it as sent mail. The `NotificationCallbacks` import supplies the parameter types: provision callbacks receive `(user, url)`, except invitation `(invitation, url)` and email change `(user, newEmail, url)`; the notice callbacks receive `(previousEmail, user)` for `emailChanged` and `(user, context)` for password notices.

```ts
// app/services/account_kit_notifications.ts
import { open, mkdir } from 'node:fs/promises'
import { constants } from 'node:fs'
import { dirname } from 'node:path'
import app from '@adonisjs/core/services/app'
import type { NotificationCallbacks } from 'adonisjs-account-kit'

async function capture(kind: keyof NotificationCallbacks, recipient: string, url?: string) {
  if (app.inProduction) throw new Error('Configure account message delivery before production')
  const path = app.makePath('tmp', 'account-kit-notifications.jsonl')
  await mkdir(dirname(path), { recursive: true })
  const file = await open(
    path,
    constants.O_WRONLY | constants.O_APPEND | constants.O_CREAT | constants.O_NOFOLLOW,
    0o600
  )
  try {
    if (!(await file.stat()).isFile()) throw new Error('Capture path must be a regular file')
    await file.chmod(0o600) // Also tighten permissions when the file already exists.
    await file.writeFile(JSON.stringify({ kind, recipient, url }) + '\n')
  } finally {
    await file.close()
  }
}

export const accountKitNotifications: NotificationCallbacks = {
  passwordResetProvision: (user, url) => capture('passwordResetProvision', user.email, url),
  accountActivationProvision: (user, url) =>
    capture('accountActivationProvision', user.unverifiedEmail ?? user.email, url),
  invitationProvision: (invitation, url) => capture('invitationProvision', invitation.email, url),
  emailChangeProvision: (_user, newEmail, url) => capture('emailChangeProvision', newEmail, url),
  emailChanged: (previousEmail, _user) => capture('emailChanged', previousEmail),
  passwordResetCompleted: (user, _context) => capture('passwordResetCompleted', user.email),
  passwordChanged: (user, _context) => capture('passwordChanged', user.email),
}
```

The policy pillar records registration as `open`, `closed`, or `application`. Additional `registrationFields` each name an application-owned model property, a primitive type, whether it is required, and an optional string `maxLength`. Generated validation and mapping admit only those fields; protected account properties and unknown request fields are rejected. Password policy uses `minLength` (default 8), `maxLength` (default null), `letters`, `mixedCase`, `numbers`, `symbols` (all false), and `minScore` (default 0). Setup rejects limits above the service's 256-character ceiling or a maximum below the minimum. Login verification of existing passwords is independent of the new-password policy. Invitation permission and restricted-account hooks are application policies; setup blocks affected activation when they are missing. Every selection with `authentication` must set `policy.accessRestrictionHook` to true and provide `app/services/account_kit_policy.ts` exporting `accountKitPolicy` with an async `canAccess(user, trx)` function that evaluates your restricted-account rule and returns a boolean. Set the flag to false only when no authentication strategy is selected. The API example sets it to true; create the callback module before running its preview. The callback must reflect your real application policy rather than a placeholder that always allows access. Selecting invitations also requires that export to provide `authorize` and `onInvitationAccepted` callbacks. Setup imports this application-owned service but does not write a default allow-all policy.

Social identity is recorded separately. The default records it as not applicable because no provider is selected. A selected Google or GitHub provider is `approved-pending` until the social implementation is installed and verified. That status is not a readiness claim.

Setup flags control the operation, committed choices control runtime policy, and environment references supply deployment values. There is no remembered wizard state. Noninteractive setup requires `--input`; missing or unsupported fields produce a nonzero result with the field name. Unknown JSON fields are rejected so a secret cannot be silently persisted. `--retirement-maintenance-window` is only relevant when retiring password login and records the operator's assertion that credential changes are stopped during the transition.

## How it works

### The full plan appears before a write

Setup inspects package dependencies, named guards, database configuration, existing routes, generated migration names, and setup files without executing application code or reading secret values. The report lists all six pillar outcomes, file actions, selected endpoint names with methods and prefixed paths, prerequisites, diagnostics, migration state, delivery mode, and distinct readiness states. Existing installations also preview by default. A missing required package, differing generated file, selected method/path collision, unsupported schema, or missing mandatory policy blocks `--apply` before any write. Install missing packages explicitly, resolve the named collision, and run setup again.

Route inspection checks literal application routes in `start/routes.ts` against the selected managed method and path using the package's managed-route overlap rules. A visible route with an unresolved parameter constraint is treated as a possible conflict and blocks apply. Grouped, imported, or programmatically generated routes cannot be certified by this static inspection; the package checks the committed Adonis route graph when the application boots. Run that boot check and exercise selected endpoints before treating the route integration as verified. `configurationValid` in the static report does not certify the executable route graph or set `workflowVerified` or `productionReady`.

### A repeated run can recover from interruption

Setup takes an exclusive `.account-kit-setup.lock` while applying. Stop other editors and setup processes in that workspace during apply; the lock coordinates setup runs but cannot make arbitrary noncooperating editor changes atomic. Every planned file is checked before any planned write and again before its own write. New files are published only after complete temporary content exists, without replacing a destination. Identical files are skipped. Generated files owned by setup and the required `adonisrc.ts`, `start/routes.ts`, and `start/kernel.ts` entries can be updated; unrelated application content, existing `.env` files, and stored account data are preserved. If interrupted, inspect a leftover lock before removing it, then rerun with the same choices. Setup stores new choices last so partially applied reconfigurations remain recoverable. Removing a managed login route while keeping its underlying authentication configuration is a route choice, not credential retirement. Removing the authentication configuration triggers `kit.authentication.retirementImpact({ passwordLogin: false })`, a read-only scan of configured user IDs and the user adapter's `hasPassword` truth. Setup reports the inspected and affected counts and blocks if any account would lose its last usable login. The owner must migrate those accounts to a confirmed alternative first. Even a zero count requires `--retirement-maintenance-window`; the scan is point-in-time and cannot protect a live application against concurrent credential changes. Social providers remain unavailable as alternatives until installed identity inventory can prove a confirmed, usable method. Preserved credential rows alone do not demonstrate access.

### Readiness is evidence, not a single setup flag

The report distinguishes generated configuration, valid configuration, applied migrations, external integrations, and verified workflows. The command does not claim production readiness from static inspection. A production check rejects insecure public origins, memory-only session persistence, and unverified session settings. The presence of application-owned policy or notification files cannot prove their callback contracts or delivery behavior, so the report keeps those checks unresolved until runtime verification. It reports unresolved sender, destination, permission, guard, and revocation work by field name without printing the environment values.

## Files delta

- `config/account_kit_setup.json`: versioned six-pillar application choices.
- `config/account_kit.ts`: selected service capabilities, password and registration policy, trusted action URLs, and maintained Mail or explicit application notification callbacks. A differing existing config stops setup before any write.
- `start/account_kit_routes.ts`: explicit package-maintained route mount using the selected existing guard adapter and named exclusions. Setup adds one import to `start/routes.ts` without replacing its routes. Disabling the last managed group changes this owned file to an inert marker, so the retained import registers no endpoints.
- `app/services/account_kit_guard.ts` and `app/middleware/account_kit_access_middleware.ts`: the selected existing guard adapter and the same account access gate for application-owned protected routes. `app/middleware/account_kit_proof_headers_middleware.ts` applies proof response headers before parser and CSRF failures.
- `config/session.ts`: for managed session routes, setup wraps a conventional `defineConfig` export with `protectManagedSessionConfig` only when it can resolve the selected direct top-level native database or development memory factory imported from `@adonisjs/session`. For `store: env.get('SESSION_DRIVER')` (or another direct environment selector), setup checks the process environment first, then the application environment files in Adonis loading order. It reads only that selector's assignment and accepts a direct store name; interpolation, duplicate or malformed assignments, linked files, and unresolved selections block apply. It does not include environment values in its report. The same scoped resolution checks the selected `DB_CONNECTION` before certifying its database client. Setup inspects executable TypeScript structure and blocks unsupported or ambiguous configuration expressions before writing; it does not execute application configuration. A custom or indirect selected factory needs an application-owned wrapper with a truthful verifier for actual server-side revocation. The deployed store still requires an application boot and logout replay check. Setup removes only its marked integration when managed sessions are disabled; edits to that integration stop reconciliation before any write.
- `adonisrc.ts` and `start/kernel.ts`: only missing required provider and middleware imports are added to their existing arrays; other entries are preserved.
- `.env.account-kit.example`: names of required deployment references with empty safe examples. Existing `.env` files and ignore rules are untouched.
- `database/migrations/*_account_kit_*.ts`: the package's reviewed schema migrations, rendered for the selected users table and identifier type. The baseline account tables and columns are proposed even when a capability is initially disabled, so later opt-in does not depend on an implicit schema installation. Existing same-name migrations must match; they are never rewritten.

## Manual steps

1. Explicitly install any reported missing packages with `pnpm add`. Setup does not install dependencies. If `@adonisjs/limiter` is missing, also run `pnpm exec node ace configure @adonisjs/limiter`; check that its provider is registered and `config/limiter.ts` uses `defineConfig` with a selected, configured store. A package install alone does not configure its runtime service.
2. Review migration content and apply it with `node ace migration:run` during the chosen deployment window. Application startup does not run migrations.
3. Review the generated route mount and configure the selected guard's application model. Implement application-owned notification callbacks or configure maintained Mail. No application-authored controller is needed for an enabled managed endpoint.
4. Supply and validate deployment environment values, the user adapter and model contract, invitation permission, restricted-account policy, and any frontend pages that collect passwords or complete email actions. Attach the generated account access middleware to application-owned protected routes so credential revocation applies there as well. For a session guard, select a configured server-side session store, apply its table migration when using the database store, and verify logout rejects replay of the old cookie. Cookie-only storage cannot enforce this revocation. Managed sessions require `protectManagedSessionConfig` in `config/session.ts` before SessionMiddleware starts; setup wires a conventional inspected database or development memory store. If your config uses a custom syntax or store, integrate the public helper yourself and provide a verifier that establishes central destroy and revocation on the actual selected store. A method-shape check alone does not establish that for a custom store. Also verify cookie security, CSRF bootstrap, trusted origin/proxy configuration and session persistence. If the application's Shield config enables CSRF conditionally, set its condition for the selected session guard (the conventional example uses `ACCOUNT_KIT_AUTH_STRATEGY=session`), then exercise the CSRF bootstrap and a protected POST against the running application. Middleware registration alone does not prove CSRF is enabled. For a token guard, verify issuance, lifetime, abilities, revocation and safe client storage.
5. Run `node ace account-kit:setup --check --production` after the application integration and exercise the selected workflows over HTTP. The command's static report cannot substitute for those end-to-end checks.
