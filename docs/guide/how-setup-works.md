# How setup works

Why `account-kit:setup` previews before it writes, how a repeated run recovers, and why its report
separates readiness states. For the steps, see [guided setup](setup.md).

### The full plan appears before a write

Setup inspects package dependencies, named guards, database configuration, existing routes, generated migration names, and setup files without executing application code or reading secret values. For selected social providers it checks Ally presence, callback origin and path, credential references, and existing Ally config without replacing it. The report lists all six pillar outcomes, file actions, selected endpoint names with methods and prefixed paths, prerequisites, diagnostics, migration state, delivery mode, and distinct readiness states. Existing installations also preview by default. A missing required package, differing generated file, selected method/path collision, unsupported schema, or missing mandatory policy blocks `--apply` before any write. Install missing packages explicitly, resolve the named collision, and run setup again.

Automatic Lucid model inspection supports a contained `#models/user` mapping to a direct `BaseModel` class or the stock `UserSchema`/`withAuthFinder` composition. The effective model, including inherited and overridden column decorators, must expose one physical `id` primary column with the chosen TypeScript identifier type. Package import aliases must resolve to the files inspected. Custom class decorators, constructors, decorated accessors, runtime metadata hooks, and other dynamic class initialization need manual reconciliation before setup can safely generate matching migrations. Static inspection cannot establish the result of application code at boot.

Route inspection checks literal application routes in `start/routes.ts` against the selected managed method and path using the package's managed-route overlap rules. A visible route with an unresolved parameter constraint is treated as a possible conflict and blocks apply. Grouped, imported, or programmatically generated routes cannot be certified by this static inspection; the package checks the committed Adonis route graph when the application boots. Run that boot check and exercise selected endpoints before treating the route integration as verified. `configurationValid` in the static report does not certify the executable route graph or set `workflowVerified` or `productionReady`.

### A repeated run can recover from interruption

Setup takes an exclusive `.account-kit-setup.lock` while applying. Stop other editors and setup processes in that workspace during apply; the lock coordinates setup runs but cannot make arbitrary noncooperating editor changes atomic. Every planned file is checked before any planned write and again before its own write. New files are published only after complete temporary content exists, without replacing a destination. Identical files are skipped. Generated files owned by setup and the required `adonisrc.ts`, `start/routes.ts`, and `start/kernel.ts` entries can be updated; unrelated application content, existing `.env` files, and stored account data are preserved. If interrupted, inspect a leftover lock before removing it, then rerun with the same choices. Setup stores new choices last so partially applied reconfigurations remain recoverable. Removing a managed login route while keeping its underlying authentication configuration is a route choice, not credential retirement. Removing password login or a selected social provider triggers `kit.authentication.retirementImpact({ passwordLogin, providers })`, a read-only scan of configured user IDs, the user adapter's `hasPassword` truth, and confirmed social identity rows. Setup reports the inspected and affected counts and blocks if any account would lose its last usable login. The owner must migrate those accounts to a confirmed alternative first. An unavailable inventory fails closed. Even a zero count requires `--retirement-maintenance-window`; the scan is point-in-time and cannot protect a live application against concurrent credential changes. Pending or quarantined social identities do not count as usable login methods, and preserved credential rows alone do not demonstrate access.

### Readiness is evidence, not a single setup flag

The report distinguishes generated configuration, valid configuration, applied migrations, external integrations, and verified workflows. The command does not claim production readiness from static inspection. A production check rejects insecure public origins, memory-only session persistence, and unverified session settings. The presence of application-owned policy or notification files cannot prove their callback contracts or delivery behavior, so the report keeps those checks unresolved until runtime verification. It reports unresolved sender, destination, permission, guard, and revocation work by field name without printing the environment values.
